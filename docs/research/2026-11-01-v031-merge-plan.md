# v0.3.1 merge plan — positives, negatives, verdict

Status: pre-run record
Date: 2026-11-01
Question: can a weight-space merge of v0.2.0 and v0.3.0 recover the
final-checkpoint regression and make v0.3.0 a little better, at zero GPU cost?

## The observation

The v0.3.0 second epoch's best in-training **100-batch** val was **2.7255 at step
6,500**. The final checkpoint at step 6,770 scored **2.7743**. The last 270 steps
cost **0.049 nats**. The step-6,500 checkpoint was overwritten: `save_checkpoint`
writes one `ckpt.pt` every 30 minutes, and EMA was off.

## Positive points

1. **Zero GPU.** The merge and evaluation run on Kaggle CPU; no training budget.
2. **Bounded downside.** If no merge beats 2.7743, v0.3.0 stays exactly as it is.
3. **Valid operation.** v0.3.0 is a continuation of v0.2.0, so their weights lie
   on a connected path; a weighted average is a legitimate model soup.
4. **Tests a real regression.** The final checkpoint is measurably worse than a
   point the model already reached. A merge may recover some of that 0.049.
5. **Reuses the fixed protocol.** 100-batch val, 2k benchmark and CL-0 are the
   same measurements that made v0.3.0 a release candidate.
6. **No laptop compute.** Everything runs in a Kaggle CPU kernel.

## Negative points

1. **The merge may be worse than both parents.** Weight averaging is not
   guaranteed to help; the v0.3.0 final may already be the best checkpoint.
2. **The 6,500 point is not the canonical final.** 2.7255 is an in-training
   100-batch eval, not the registered 100-batch final; the difference may be
   noise, and the final 2.7743 is the number the release is built on.
3. **The configs differ.** v0.2.0 and v0.3.0 have different `train` sections
   (steps, seed, re-warm), so the merge tool's full-config check would reject
   them. A model-only compatibility check is required.
4. **The 2k benchmark is noisy.** A val win may not transfer to the benchmark;
   only a no-regression check at 2k can tell.
5. **CPU eval is slow.** Four val runs at ~28 minutes each, plus the best 2k and
   CL-0, is ~3–5 CPU-hours. It fits the CPU quota but is not instant.
6. **It does not fix the root cause.** The real fix is a best-checkpoint
   callback and a lower-LR continuation; the merge is a zero-cost probe, not a
   substitute.

## Verdict

**Do the merge first.** It is free, bounded and tests a real regression. If no
merge beats **2.7743**, keep v0.3.0 and run the **500-step lower-LR continuation
with a best-checkpoint callback** (~2.5–5 GPU-h). Do not run the data-mix
experiment until those two are resolved.

## Protocol

- v0.2.0 weight **0.1 / 0.2 / 0.3**; v0.3.0 weight **0.9 / 0.8 / 0.7**.
- v0.3.0 baseline at weight 0.0 must reproduce **2.7743** as a sanity check.
- Best merge → 2k benchmark + CL-0.
- Release gate: val < **2.7743**, no 2k task regresses by >2σ vs v0.3.0, CL-0
  ≤ **2.763648** (v0.3.0's 2.756648 + 0.0070).
- If no merge passes, `release_candidate=false`; keep v0.3.0.

## What this is not

- Not a new model architecture.
- Not a substitute for the best-checkpoint fix.
- Not a data experiment. The TinyStories-heavy mix (20%) is the next data lever,
  but only after the free merge and the continuation are resolved.
