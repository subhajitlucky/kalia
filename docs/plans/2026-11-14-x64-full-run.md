# X64 v150 full run — Nov 14 execution plan

Status: **prepared 2026-11-10, execute after the Nov 14 Kaggle quota refresh.**
This is the runbook for the registered X64 150M depth-expand, not a new
experiment. The smoke passed: init val **2.7731** (gate 2.9079), throughput
**6.5–6.9k tok/s** on 2×T4.

## 1. What is being run

- Model: v0.3.1 depth-expand, **10 → 38 layers**, **147,803,904 params**,
  width 512, 8 heads, 1k context, GPT-2 BPE 50,257.
- Init: zero-init identity insertion; init val 2.7731.
- Data: `kalia-prep-v2b` 2.4B tokens.
- Training: 4,770 steps × 524,288 tokens = 2.5B tokens; Muon 0.01,
  AdamW 3e-4, cosine, warmup 200.
- Expected wall time: **~103.6h at 6.7k tok/s**; 120h budget leaves ~16h
  for evaluation and restarts.
- Public base stays **v0.3.1** until the 9-task gate and capability regression
  pass.

## 5. Per-session runbook

### 5.1 Before pushing

```bash
cd /home/subhajit/project/kalia
git status --short          # must be clean
git log --oneline -1        # confirm the pinned commit
```

Check the HF repo:

```bash
.venv/bin/python - <<'PY'
from huggingface_hub import list_repo_files
print(list_repo_files("kalia-lm/kalia-v150-run"))
PY
```

- **Session 1:** the repo should have no `checkpoints/ckpt.pt` and no
  `run_started.json`.
- **Sessions 2+:** `checkpoints/ckpt.pt` must exist. If it is missing but
  `run_started.json` exists, the kernel aborts by design. Restore the
  checkpoint or deliberately remove the marker before restarting.

### 5.2 Push the kernel

```bash
rm -rf /tmp/kalia-x64-v150-full
mkdir -p /tmp/kalia-x64-v150-full
cp tools/kalia_x64_v150_full_kernel.py /tmp/kalia-x64-v150-full/
cp kaggle/kernel-metadata-x64-v150-full.json \
   /tmp/kalia-x64-v150-full/kernel-metadata.json
.venv/bin/kaggle kernels push -p /tmp/kalia-x64-v150-full
```

The kernel runs one 7.5-hour session (`MAX_MINUTES = 450`). It checks the HF
repo: first session expands v0.3.1 and uploads `run_started.json`; later
sessions pull `checkpoints/ckpt.pt` and continue.

### 5.3 Monitor

```bash
.venv/bin/kaggle kernels status subhajitlucky/kalia-x64-v150-full
```

Kaggle's API often shows no live log; the reliable progress signal is the HF
repo's `checkpoints/ckpt.pt` timestamp and the `logs/train_log.csv` step count.
Check every 30–60 minutes.

At the end of the session:

```bash
.venv/bin/python - <<'PY'
from huggingface_hub import hf_hub_download
p = hf_hub_download("kalia-lm/kalia-v150-run", "logs/session_manifest.json")
print(open(p).read())
PY
```

Record `steps`, `tokens`, `session_val`, and tokens/s in
`docs/results/x64-full/README.md`.

### 5.4 If the session fails

1. Read the Kaggle log. Do not guess.
2. Check the last HF checkpoint step.
3. If the checkpoint exists, push the next session; it resumes.
4. If the checkpoint is missing and `run_started.json` exists, restore from the
   Kaggle output if available. Only if you accept a restart, delete
   `run_started.json` and `checkpoints/ckpt.pt` from the HF repo.
5. Never start a second session while the previous one is still running.

## 7. Evaluation after training

Stop at **4,770 steps** or 120h, whichever comes first.

### 7.1 Held-out loss

```bash
.venv/bin/python eval_val.py \
  --ckpt /path/to/ckpt.pt \
  --val-bin /path/to/val.bin \
  --batches 100 --batch-size 8 --device cuda \
  --out docs/results/x64-full/final_val.md
```

Use the **same** `kalia-prep-v2b` `val.bin` as v0.3.1. Report val and bpB.

### 7.2 Standard 9-task

```bash
.venv/bin/python eval_bench.py \
  --ckpt /path/to/ckpt.pt \
  --tasks arc_easy,arc_challenge,boolq,hellaswag,lambada_openai,openbookqa,piqa,sciq,winogrande \
  --limit 2000 --device cuda \
  --out docs/results/x64-full/bench.json
```

Gate: **mean ≥ 0.468** (+10% over v0.3.1's 0.4258). Report per-task numbers,
not just the mean.

### 7.3 Capability regression

Re-fit the captioner decoder on the 150M base (width 512 is unchanged), then
run the registered S-3 suite:

- captioner held-out ≥ 0.99;
- see→draw→see ≥ 0.90;
- self-verify ≥ 0.95;
- constraints ≥ 0.98;
- edit compiler within 2 pp;
- audio within 2 pp.

If the base fails S-1/S-2, do not spend GPU on adapters; log the null and keep
v0.3.1.

## 8. Decision gates

| gate | threshold | action |
|---|---|---|
| **S-1** held-out val | ≤ 2.70 | if fail, log and keep v0.3.1 |
| **S-2** 9-task mean | ≥ 0.468 | if fail, log and keep v0.3.1 |
| **S-3** capability regression | all bars | if fail, no promotion |
| **S-4** provenance | own weights, no distillation | must pass |

If all pass, promote the 150M to the public base (v0.x; the user decides when
it is v1). The 58M v0.3.1 remains the fallback.

## 9. Failure playbook

| symptom | action |
|---|---|
| OOM at micro 2 | set `micro_batch_size: 1`, `grad_accum_steps: 256`; same 524k tokens/step |
| throughput <6k tok/s | trim `max_steps` to 4,300; report the actual token budget |
| loss spike / divergence | stop; do not tune mid-run; log the step and keep the last good checkpoint |
| HF push fails | stop; download the Kaggle checkpoint; upload manually; do not start the next session until it is in HF |
| Kaggle kills session at 9h | resume from the last 30-minute checkpoint |
| quota exhausted | stop; resume next week; do not use a second account |
| `run_started.json` without checkpoint | restore or deliberately restart; never silently restart |

## 11. What not to do

- Do not change the data, tokenizer, or architecture mid-run.
- Do not re-warm the LR every session; `rewarm: false` is deliberate.
- Do not start from scratch if the HF checkpoint is missing; investigate.
- Do not use multiple Kaggle accounts.
- Do not promote the model before S-1/S-2/S-3.
- Do not spend the 120h on the 576×34/8k architecture; that is a donated-compute
  target.
