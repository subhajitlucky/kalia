# Kaggle free-tier plan for the 150M

Status: **recommendation, 2026-11-10.** Public base remains v0.3.1. This is a
plan, not a result.

## 1. The measured budget

Kaggle gives **2×T4 16GB**, **30 GPU-hours/week**, and a **9-hour session
limit**. The 58M v0.3.1 measured **13.6k tokens/s** in the X49 smoke.

A 147.8M model is ~2.55× the parameters, so the same recipe should run at
roughly:

```
13.6k × (58 / 147.8) ≈ 5.3k tokens/s
```

At 5.3k tokens/s and 30h/week:

| utilization | tokens/week | tokens/month | tokens/year |
|---|---:|---:|---:|
| 100% | 0.58B | 2.50B | 30B |
| 70% (realistic) | 0.40B | 1.75B | 21B |

So:

| target | time at 70% utilization |
|---:|---:|
| 5B tokens | ~3 months |
| **10B tokens** | **~6 months** |
| 20B tokens | ~11–12 months |
| 50B tokens | ~2.4 years |
| 100B tokens | ~4.8 years |
| **1T tokens** | **~48 years** |

The 1T plan is not a Kaggle plan. It is a donated-cluster plan.

## 2. Decision: depth-expand, not from-scratch

**Best model per Kaggle hour: expand v0.3.1 from 10 → 38 layers
(147,803,904 params), zero-init identity insertion, then continue pretraining
on ~10B tokens.**

Why:

- It starts from a trained function: init val should be ~2.7579, not random.
- It reuses the tokenizer, 1k context, data pipeline, and the 4×512
  multimodal interface.
- It is 2.55× larger, and 10B additional tokens is ~4× the original 2.4B
  pretraining budget.
- It is our own model growth. No external weights, no distillation, no
  borrowed inference.

The alternative — from-scratch 576×34 GQA, 8k context — is the better
architecture, but it is the wrong use of this budget:

- 10B tokens is only 67 tokens/param; 20B is 134. The model would be
  undertrained.
- 8k context and width 576 cost ~10–20% throughput and need a new 512→576
  multimodal projection.
- A from-scratch 150M at 10B tokens has no head start; the depth-expand has
  already seen 2.4B tokens before the new run begins.

**If from-scratch is non-negotiable:** use **512×38, 1k context, MHA 8/8,
FFN 1408, GPT-2 BPE**, random init, 10B tokens. Same ~6 months, but weaker at
equal tokens. Do not use 576×34/8k for a 10B-token Kaggle run.

## 3. The 10B-token run

| field | value |
|---|---|
| model | 512×38, 147,803,904 params |
| init | zero-init depth expansion; init val gate ≤ 2.9079 |
| context | 1,024 |
| tokens | 10B total: 8B new + 2B replay |
| new mix | FineWeb-Edu 65%, code 20%, math 10%, reference 5% |
| optimizer | Muon 0.01, AdamW 3e-4 |
| schedule | 500-step warmup, cosine/WSD to 10% |
| batch | 524k tokens/step (micro 4 × accum 64 × 1024 × 2 GPUs) |
| steps | ~19,073 |
| wall time | ~6 months at 70% utilization |
| eval | every 250M tokens |
| checkpoint | every 30 minutes |

Data volume: 10B tokens as uint16 is **20GB**; 8B new tokens is only ~0.5% of
FineWeb-Edu. Storage is not the problem.

Stop rule: if val loss does not improve by **0.02 nats over 2B tokens**, stop
and keep v0.3.1. Do not tune after the result.

## 4. Why not the 1T / 576×34 plan

- 1T tokens is ~48 years on free Kaggle.
- 20B tokens is ~1 year; even that is only 134 tokens/param.
- 576×34 GQA is the better long-term architecture, but the token budget is the
  bottleneck, not the shape.
- MoE, MLA, Engram and Gated DeltaNet are not the constraint at this budget.
  Data and tokens are.

## 5. Capability plan after the base

A 150M base alone will not be “GPT-6 level” in biology, math, reasoning and
coding. The realistic path is a system:

| domain | module |
|---|---|
| biology | retrieval over permissive textbooks/PubMed OA; citation verifier |
| math | Python/SymPy tool; model writes the plan, tool computes |
| coding | code execution + unit tests; best-of-N selection |
| reasoning | chain-of-thought + best-of-N + verifier |

Adapters are cheap compared with the base:

- biology LoRA: ~0.5B tokens of permissive biology text;
- math LoRA: ~0.5B tokens of OpenWebMath/FineMath + procedural;
- code LoRA: ~1B tokens of permissive code.

RLVR stays a documented probe, not a promise: the 135M GRPO probe was
negative (GSM8K 1.82 → 1.59).

## 6. Gates

- **G1** standard 9-task mean ≥ **0.468** (+10% over 0.4258).
- **G2** capability regression: captioner ≥ 0.99; see→draw→see ≥ 0.90;
  self-verify ≥ 0.95; constraints ≥ 0.98; edit compiler within 2 pp; audio
  within 2 pp.
- **G3** provenance: own weights, no distillation, no teacher-generated text.
- **G4** reproducible config, data manifest, and ledger hash.

If any gate fails, keep v0.3.1 and log the boundary.

## 7. Next steps

1. Verify the zero-init smoke: init val ≤ 2.9079 and ≥100 steps without OOM.
2. Build the 10B-token mix (8B new + 2B replay), GPT-2 BPE, 20GB uint16.
3. Run a 2B-token pilot; measure actual 150M throughput and val curve.
4. If the pilot is stable, continue to 10B over ~6 months.
5. Re-fit the captioner/diffusion/audio adapters and run the 9-task gate.

## 8. The 120-hour sprint (4 weeks)

If the budget is **120 GPU-hours total**, the choice is still **depth-expand, not
from-scratch**.

Why: 120h at the conservative 5.3k tokens/s is **~2.3B tokens**. A random-init
150M on 2.3B tokens is only ~15 tokens/param; it will be undertrained and
probably worse than v0.3.1 (which already saw 2.4B). The depth-expand gets the
same 2.3B tokens **plus** the v0.3.1 head start.

What 120h buys at different sustained throughputs:

| sustained 150M throughput | tokens in 120h | X64 2.4B run |
|---:|---:|---:|
| 5.3k tok/s (smoke estimate) | 2.3B | ~126h; trim to 4,500 steps |
| 6.7k tok/s (X64 prereg estimate) | 2.9B | ~100h |
| 10k tok/s | 4.3B | ~67h; ~53h left |
| 42.7k tok/s (58M full-run scaled) | 18.4B | ~16h; ~104h left |

The repo has two conflicting throughput anchors: the 50-step smoke says 13.6k
tok/s on the 58M, while the completed v0.2.0 run implies ~109k tok/s. The X64
smoke is the measurement that settles it. Plan conservatively; treat anything
above 10k tok/s as upside.

Recommended 120h allocation:

1. **0–3h:** verify the zero-init smoke; measure 150M throughput.
2. **3–100h:** X64 full continued pretraining, 4,770 steps / 2.4B tokens.
   If the measured throughput is <6k tok/s, trim to 4,500 steps to fit 120h.
3. **100–110h:** 9-task eval and capability regression.
4. **110–120h:** if the run finished early and throughput is >10k, use the
   remaining hours for a pre-registered second stage on new data (2–6B tokens),
   not for a from-scratch restart.

Do **not** start a random-init 150M in this window. At 2–4B tokens it is
undertrained; at 18B it is only at the edge of viability, and it still lacks the
v0.3.1 head start. The 58M continuation is the compute-matched control, not the
150M deliverable.
