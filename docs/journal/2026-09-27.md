|---|---|---|---|---|
| ctl-s1337 | 3.7924 | 4.0700 | 9.2314 | 5.1614 |
| ctl-s1338 | 3.9708 | 4.0345 | 9.0945 | 5.0600 |
| rev-s1337 | 3.8698 | 4.0963 | 9.3066 | 5.2103 |
| rev-s1338 | 4.0583 | 4.1343 | 9.4170 | 5.2827 |

Seed-pair means: control gap **5.1107**, treatment gap **5.2465** (Δ +0.136,
wrong direction); control val **3.8816**, treatment val **3.9641** (Δ +0.083).

- P1 (control gap > 0.3 nats): **CONFIRMED** — the entry–exit asymmetry is
  already ~5.1 nats at 30M parameters, consistent with 6.06 nats at 58M.
- P2 (gap closes by ≥ 0.10): **FAILED**.
- P3 (forward loss within +0.02): **FAILED**.

Both seeds moved the same wrong direction on both metrics.

**Interpretation:** reversing chunk *order* while preserving intra-chunk order
does not transfer to token-level reversal. The transform mildly hurts. A
stronger form (token-level reversal, or a lower reversal ratio) is a separate
hypothesis for a later cycle, not a silent retry.

**S-A FAILS**: the registered rule allows no task to regress by more than 1.0 pp,

**Two things must be said alongside it, both registered in advance:**

1. **The comparison is confounded with the corpus change.** v0.1.2 trained on
   the original corpus; v0.2.0 on the compliance rebuild, which replaced the code

   attributing any v0.2.0-vs-v0.1.2 quality difference to the model rather than

2. **Loss and accuracy moved in opposite directions.** Deterministic val loss on

   loss gap), and it is the first direct evidence in this project for D5
   ("select on benchmarks, not loss alone"). It is *consistent with* that finding
   and *also* confounded by the corpus change, so it is suggestive, not proof.

**These are interim numbers.** v0.2.0 is at 73% of its schedule; session 3 has
not run. The final numbers come after it, and the kernel is idempotent — one

## I15 — training windows ignored document boundaries

Found while auditing `data.py` on 2026-09-28, after the v0.2.0 final-evaluation
pre-registration was written. Two related defects, both measured on our own
`val.bin` rather than assumed.

**The corpus is EOS-delimited and we never used that.** All four sources carry
the same delimiter (GPT-2 EOS, 50256) at comparable rates — FineWeb-Edu 2.15,
TinyStories 4.58, Cosmopedia 4.92, code 5.04 per 1k tokens, median document
~195–213 tokens. `TokenDataset.get_batch` samples contiguous windows with no
document awareness, and `CausalSelfAttention` uses a plain causal mask. Because
documents are ~5x shorter than the 1024-token context, **nearly every training
window crosses at least one boundary**, and the model attends across all of it.
Llama 3, SmolLM3 and OLMo 3 all mask this.

**Worse, the mixer destroys document structure before training sees it.**
`mix_bins.py` writes `block_tokens: 1_000_000` — the training file is a
60/20/15/5 round-robin of four corpora in million-token blocks, with no separator
at the joins. Observable in the data: the four slice means differ sharply
(4346 / 5018 / 5620 / 2650 token IDs) and the code slice is clearly distinct.
So **0.307% of windows straddle a corpus boundary** and splice TinyStories
directly into code. Verified present, roughly 0.3% of windows.

**Why it was never noticed.** Nothing in the pipeline had a notion of a document,
so no loss curve or benchmark could reveal it — the defect is invisible to every
metric we had been optimising. It surfaced only from reading the mixer.

**Fix and cost.** `document_mask()` builds a block-diagonal causal mask plus a
loss mask dropping targets that open a new document; enabled per-arm via a config
field, off by default, with tests asserting the unmasked path is unchanged. The
pre-registered ablation is X17 (bar: 0.010 nats, the same threshold D15 used to
reject Muon+). Honest caveat recorded in advance: the micro context of 512 makes
boundary-crossing *more* frequent than the real 1024, so a micro pass likely
overstates the full-scale gain.

**Process lesson.** Two of our three data-integrity discoveries in one week (I14
log truncation, I15 document boundaries) were invisible to loss and benchmarks.
The checks that find them are cheap and specific: verify the published log starts
at step 10; verify the corpus is parseable into documents. Both are now routine.

## I14 — the published training log was incomplete for two days

Found while monitoring v0.2.0: `kalia-lm/kalia-v012`'s `logs/train_log.csv` began
at step 1740, so sessions 1–2 of v0.1.2 (347 logged steps, the whole descent
from 10.7 to the plateau) were missing from the public record.

**Root cause (timestamps, not speculation).** Log persistence on resume
(`train.py`, restoring the CSVs from the hub before appending) landed in commit
`3afb435` at 2026-09-23 06:00 UTC. v0.1.2's session 1 ended at 05:10 UTC (last
push `f093c311`) and session 2 started immediately after — running the pre-fix
code, which truncated the log at 1740. Session 3 ran the fixed code, pulled
session 2's log, and appended. So the *only* lossy session was session 2, and the
cause was a mid-run code change, not a bug in the current code.

**Recovery.** HF keeps per-file commit history, so the lost epoch was
reconstructed from the repo itself: 173 rows at revision `f093c311` (steps
10–1730) plus 174 rows at HEAD `650ea5e1` (steps 1740–3470). The merge is
contiguous — 347 rows, steps 10→3470, monotonic, no step gap other than the
10-step log interval. The val log was recovered the same way (13 points, steps
250→3250, revisions `3f8a82bf` + `650ea5e1`).

Both merged files are now in `docs/curves/` and have been **republished** to
`kalia-lm/kalia-v012` (`logs/train_log.csv`, `logs/val_log.csv`). The overwrite
is strictly additive: the previous file is a subset and remains in the repo's
commit history either way.

**What the recovered curve adds.** The val log now shows the part that was
missing, and it supports D41 rather than complicating it: 4.0881 (250) → 3.2859
(500) → 2.9836 (750) → 2.8100 (1000) → 2.6108 (1250) → 2.5270 (1500), then
oscillation inside 2.40–2.63 for the remaining 1,750 steps with a single best
point (2.3986 at step 3,000). The descent is real and early; the last third of
the schedule is a plateau. Stopping at 3,478 kept the plateau, not the gains.

**Process change.** A resumed session now restores its logs before appending, and
this incident is the reason that behaviour is treated as load-bearing rather than
incidental: a log gap is invisible until someone diffs the curve against the
schedule. Verification added: after every session, check that the published
`train_log.csv` starts at step 10 and its last step matches the checkpoint.

## v0.2.0 monitoring — the val sets are not comparable (D43)

v0.2.0's first validation point looked alarming: **val 4.8272 at step 250**
against v0.1.2's **4.0881** at the same step, while v0.2.0's *training* loss was
slightly *better* (mean −0.11 nats over the first 190 shared steps). Train better
and val worse points at the evaluation data, not the model.

**Confirmed by direct measurement.** Both `val.bin` files are 10M tokens, but
they are not the same bytes — they are identical for the first 200,000 tokens and
diverge after that, consistent with the compliance rebuild replacing a source
slice. Evaluating the *published v0.1.2 weights* on both, same seed, same 25
batches (204,800 tokens):

| v0.1.2 model on | loss | bpB |
|---|---|---|
| v1 val (original prep) | 2.3915 | 0.8032 |
| v2b val (compliance rebuild) | 3.1070 | 1.0168 |

The val set alone accounts for **+0.72 nats** — effectively the whole apparent
regression (+0.74 at step 250). v0.2.0 is not behind; it is being scored on a
harder set.

Confirmed at the full published protocol (100 batches, 819,200 tokens, seed
1234 — the identical setting behind the originally published 2.4366): v0.1.2
scores **3.0533 / 0.9992 bpB** on the v2b val set. That is the number to compare
against from now on; 2.4366 / 0.8184 remains true for the old set alone.

**Decision D43:** `kalia-prep-v2b`'s `val.bin` is the canonical held-out set for
all future comparisons, and v0.1.2 is re-baselined on it (**3.1070 / 1.0168 bpB**
at 25 batches, pending the 100-batch confirmation). The previously published
2.4366 / 0.8184 bpB remains a true measurement of v0.1.2 — on the *old* val set —
and must never be placed in a table beside a v2b number. Within-version
comparisons (including the J2 stopping rule, which compares a version against
itself) are unaffected.

The lesson is specific and cheap to honour: a corpus rebuild silently redefines
the yardstick, so any number that crosses a rebuild boundary has to be
re-measured on both sides before it is believed.
