## I22 — Kaggle hard-enabled nbformat cell-id validation; runs died blank

Roughly six runs failed in a row with an *empty* failure message, zero log
lines, and no output files — including a fresh kernel id, a CPU variant, and a
trivial one-cell notebook. The publish kernel had hit the same signature once
earlier and recovered on re-push, so it read as flake.

The bisection that found it: script kernels ran; notebook kernels failed; a
minimal notebook with proper cell `id` fields ran; the same notebook without
them failed. Kaggle promoted its long-standing `MissingIDFieldWarning` to a
hard error mid-day, exactly as the warning said it would.

Fixes: both active builders emit `id` per cell; all 30 notebooks normalized to
carry ids; `tools/check_notebooks.py` now fails loudly on any id-less notebook,
so the next regeneration cannot reintroduce this silently. Five probe kernels
deleted.

**Lesson:** a blank pre-flight error plus zero logs means the *artifact* never
executed — bisect the artifact type (script vs notebook, with vs without the
suspect field) before touching the code.

## Step 1 — the 58M control seed spread, confirmed, and the registered stop

|---|---|---|---|
| v030-ctl-s1401 | 3.8045 | 3.8086 | +0.0041 |

Cost: two sessions, ~6.6 h each (500 steps x 262,144 tokens per arm at the

Decision (user, same day): **pivot to visible-gain work** — retrieval helper and

## Tier 1, same day: the copy test, the distraction, and the selector that hurts

The frontier re-check (`docs/research/2026-10-08-frontier-recheck.md`) said the
sub-7B retrieval-utilization failure might not transfer here, because KALIA is a
base story model and verbatim copying is a narrower task. Measured today with
`retrieval_probe.py` — CPU, deterministic, bootstrap CIs over items:

- **Copy works at 58M.** Oracle context: top-1 0.828 [0.734, 0.922] against a
  0.125 chance level; without context 0.000. A fact placed one sentence before
  the question is usable. But with BM25 top-3 — which never missed the true
  passage — accuracy falls to 0.297. The bottleneck is picking among confusable
  passages, not retrieving the right one.
- **Distraction is real and paired.** Irrelevant context raises the NLL of
  held-out continuations by +0.1222 nats [+0.077, +0.171]; relevant context
  lowers it by −0.1075 [−0.179, −0.046]. Both intervals exclude zero, on 48
  paired windows of real text.
- **The log-prob selector hurts.** selected − greedy = −0.281 [−0.406, −0.172];
  coverage (the ceiling any selector could reach) is 0.953. Scoring the whole
  4-token continuation lets a fluent wrong answer out-score a correct first
  token, so `best_of_n.py` as implemented is the negative control, not the
  mechanism. Score the decision position, or learn a SCATR-style head, against
  the measured ceiling.

Consequence: a lookup feature is defensible as a *tool* — passages surfaced to
the user, strict copy templates — not as prompt-stuffing for story generation.
Reopen the plan only with the selector fixed and re-measured.

**Selector fix measured (kernel v6).** Scoring only the decision position
(`score_tokens=1`) reproduces greedy exactly — delta +0.000 [0.000, 0.000] —
and removes the −0.281 harm; k=2 still hurts (−0.125). At 58M the own-verifier
best-of-N cannot beat greedy: the candidates exist (coverage 0.953), but the
information needed to pick them is not in the model's own log-probabilities.
The head, not the configuration, is the remaining path.

## I24 — the contamination gate reported 63,491,977 hits, and every one was whitespace

The L20-style gate (13-gram, token level, exact-verified) ran over the full 2.4B
token corpus against the five scored benchmarks. Its first completed scan
reported **63,491,977 PIQA matches** — five orders of magnitude more than any
other task. That count was not a finding; it was the bug report.

120 PIQA rows carry copied web text with long runs of spaces ("Peppermint
    Fennel    Coriander         Steeping Instructions..."). Tokenized, those runs
produce all-space 13-grams, and an all-space window matches Python indentation
in the corpus millions of times. Fix: pattern windows must carry at least six
distinct token ids (`MIN_DISTINCT`), which any real sentence satisfies and
runs, padding and separator art cannot. A second artifact was caught the same
way: ARC's `choices` field is a dict, and stringifying it produced Python-repr
patterns ("['A', 'B', 'C', 'D', '") that matched quiz-like code 601 times; the
extraction now reads `choices["text"]` explicitly.

Operationally, the fourth run also executed a stale staged runner because the
push did not re-copy `tools/kalia_corpus_gates_kernel.py` into the staging
directory — the kernel's code file is pushed from staging, while the repo copy
only feeds the dataset. The failure mode was visible (LAMBADA still failed to
fetch with the old error) and the fix is bookkeeping, not code.

**Final, clean result** (`docs/results/corpus-gates.json`): 2,903 verified
windows in 2.41B tokens (~1.2 per million) — PIQA 1,429, HellaSwag 725, ARC-Easy
377, LAMBADA 368, **WinoGrande 0** — plus 4 in the val shard. Samples are real
text: wikiHow-style instructions, ActivityNet-style captions, book dialogue,
science phrasing. The model card consequence is bounded but real: four of the
five scores may be marginally optimistic; the affected share is far below
0.001% of tokens.

The lesson is the same shape as I22's: a gate that cannot be absurd is not
being read. 63M hits is impossible, and the impossibility is what surfaced the
degenerate patterns before a single match was trusted.
