# Journal — 2026-10-12

The patha arms finished, and the day's main finding is about our own
instruments: the GPU found a bug the CPU could not.

## The bug: a device mismatch, found twice on hardware

The first X29 launch (uniform, v1) died before step 1 because the code dataset
predated `patha.py` — republished, relaunched. Then **jata died twice in a
row** with an NCCL collective-timeout signature that looked exactly like the
old x26-v2 flake. It was not a flake. `PathaReplayDataset.get_batch` drew
replay rows on CPU and new rows via `TokenDataset.get_batch`, which moves to
the target device internally — and then `torch.cat` mixed a CPU tensor with a
CUDA tensor. On CPU it passes; on GPU it raises on the very first batch, rank
1 dies, and rank 0's first allreduce waits forever for a rank that will never
arrive.

This is the **second** bug of exactly this shape: x26's `_probs` was CPU-only
tested and CUDA-broken, and the local test suite could not see either one.
Recorded as a project-level lesson: any path that receives tensors from
`TokenDataset` inherits a device contract that CPU tests cannot falsify.
Fixed by assembling every part on CPU and moving the batch once, at the end
(`d1055c5`), with a test (`test_patha.py::test_new_rows_are_drawn_on_cpu_and_moved_once`)
that spies on the device argument the dataset passes down. jata completed its
full 1000 steps on the fixed code.

## The retention instrument is running

The registered X29 retention endpoint is the CL-0 ledger on each final
checkpoint. Deployed as `kalia-x29-forget-probe` — a **CPU kernel**
(`enable_gpu: false`): retention is a measurement, not a training run, so it
must not spend the GPU budget. Guards built in: the frozen probe file is
rebuilt from canonical `val.bin` by the deterministic splitter and refused
unless its sha256 matches the instrument frozen 2026-09-28; the ledger is
seeded with the exact v0.2.0 baseline row (2.798875 at step 4770); and the
v0.2.0 checkpoint is re-scored first as a self-check before any arm number is
trusted. ghana relaunched into the freed slot (queued); krama waits for the
next quota window.

## The retention metric landed — the first arm-level movement this project has measured

CL-0 on the final checkpoints, the registered primary metric:

| row | probe_loss | drift vs pretrain best |
|---|---|---|
| v0.2.0 baseline (4770) | 2.798875 | — |
| uniform | 2.775169 | **−0.023706** |
| jata | 2.816978 | **+0.018103** |

Uniform's 1000-step update with 10% shuffled replay left the model **better
on the pretrain distribution than the pretrain itself**; jata's structured
ordering **regressed** it. The arm gap is 0.0418 nats — same instrument, same
session — and the retention ordering is identical to the val ordering from
the GPU runs (uniform better, jata worse, ~0.04 on both). Two independent
metrics, one story: at this scale, replay *order* matters, and it is jata's
forward-reverse-forward structure that hurts — the recitation order built to
preserve a text against human memory loss is not, on this first measurement,
the order that preserves it against gradient drift. (Observation, not claim;
the second seed will say whether it survives.)

No claim yet: n=1 per arm, ghana/krama pending, and the X29 registration
requires a second seed before any winner ships.

## The probe nearly scored the wrong instrument — and the guard caught it

The first three probe-kernel versions scored `data/probe/val_forget.bin`, the
2026-09-28 pretrain-era split, instead of the CL-0 ledger's actual yardstick:
the G2-pinned `corpus/probe_val.bin` (sha `1664f71a…`), published in
`kalia-lm/kalia-v020` and fingerprinted in `docs/legal/val-shard-hashes.json`.
Re-scoring v0.2.0 on the wrong file gave 2.909614 — **+0.1107** against the
recorded row. A silent substitution would have shipped a fake 0.11-nat
"regression" on every arm; the self-check refused to produce a single arm
number instead.

This is the **third** sighting of the producer/consumer probe-file mismatch
(`test_publish_contract.py` records the first two: "producer wrote
val_forget.bin, consumer wanted probe_val.bin"), and the second guard this
week to refuse bad science before it shipped (the first: the device contract
in `patha`, caught on the first GPU batch). Fixed in `d220918`: the kernel now
fetches the pinned shard from the hub, verifies its sha256 against the G2 record, seeds
the ledger with the exact baseline row, and re-scores the baseline as a
self-check before any arm is believed. That self-check reproduced the October
7 baseline to **0.000001** (2.798876 vs 2.798875) — five days, different
session, same instrument, exact.

Two smaller entries from the same hunt, kept because they will recur: the
probe kernel's first two versions died instantly on `hits[0].parent` (a
`Path` method on the `str` that `glob` returns) — the same top-level
kernel-script blind spot that CPU tests cannot see — and the Kaggle status
endpoint reported RUNNING with an empty log feed while the process had
already crashed. "RUNNING with 0 lines" is not evidence of progress; the
final status is.
