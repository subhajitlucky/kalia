## The launch-blocker: update arms never resumed (I18)

Auditing the generated notebooks against the plan found that Steps 2–4 invoked
`ablate.py` / `train.py` with **no `--resume` flag and no checkpoint source**.
Every continual-update arm would have trained from random initialisation
instead of the v0.2.0 checkpoint — the same failure class as the re-warm
defect (Status update 3): a mechanism never switched on, reporting a
plausible null after the quota is spent.

Fix: `ablate.py` takes `--resume-from-hub` and forwards `--resume --hub-repo`
to `train.py`; the rewarm/replay/kautilya notebooks pass
`kalia-lm/kalia-v020`; baseline stays fresh by design. `test_v030_resume.py`
reads the notebook JSON so a dropped flag fails locally rather than on
Kaggle. This is the fourth defect of this exact class the suite process has
caught before GPU spend.

## Addendum — two more silent-null defects found in the same audit

**I19 — the Kautilya arms would have trained zero steps.** `kalia-kautilya.yaml`
sets `max_steps: 1000` but no `update_budget`, and the notebook passes
`--max-steps 1000` (absolute ceiling). Resuming at step 4770, the loop
condition is false on entry: exit 0, no rows, quota spent. Fixed with
`update_budget: 1000` + `test_update_budget_matches_max_steps`. Fifth defect
of this class caught before GPU spend.

**I20 — Step 3 ignored Step 2's verdict.** The plan registers the replay sweep
as using "the same schedule from Step 2's outcome", but the replay arms carry
hardcoded `rewarm: true` and the notebook never read `step2_rewarm.json`. Had
Step 2 concluded against re-warming, Step 3 would have measured the wrong
schedule. The replay notebook now reads the verdict and patches the in-kernel
config copies (committed configs untouched; the run log records the choice).
